## 二、性能报告（已完成部分）

三个自编码器的潜在空间利用率均接近满维（softplus_l1 激活下有效维度 ≈ 标称维度）。**128 维验证误差最低**；256 维反而略差，说明在仅 900 张训练图上更高潜在维度没有带来收益。

### 3. 主要结论

1. **生成质量**：64 维时两种判别器旗鼓相当（保真度差距 < 0.3%）；128 维时 QSNN 判别器全面小幅领先（最终保真度 +0.85%，V_trace +2.5%，图像 MSE 更低），且判别器保持满准确率，说明 QSNN 判别器在更高维度下判别能力更强。
2. **维度扩展性**：保真度随维度上升明显下降（64 维约 0.72–0.76 → 128 维约 0.64–0.69），生成图像的像素方差也远低于真实数据（0.02–0.04 vs 0.057），存在一定模式收缩；256/784 维趋势因 run 中断无法评估。
3. **计算成本**：QSNN 判别器（cheby_suzuki 后端，含耗散演化）每 epoch 耗时约为 VQC 的 2–5 倍，显存占用约 1.5–3.6 倍；其耗散通道带来约 0.4–0.5% 的概率质量泄漏，VQC 为幺正演化、无泄漏。
4. **数值稳定性**：两个后端的 trace 漂移、厄米性漂移均在 1e-6 量级以下，模拟数值可靠。

## 三、dim256 / dim784 中断原因调查

### 现象

- `highdim_comparison/runner_status.json` 停留在 `"status": "running"`（2026-07-16 14:05:29 启动，PID 992317 / 992318），但两个进程早已不存在。
- `logs/dim256_qsnn_full.log` 与 `logs/dim256_vqc.log` 均为 **0 字节**；`logs/sequential_128_256_784.log` 只有 `START dim256`，没有 `DONE`。
- dim256 两个输出目录的最后写入时间均为 2026-07-16 14:07（qsnn 完成 3 个 epoch ≈ 108 s，vqc 完成 6 个 epoch ≈ 126 s，与 14:05:29 启动 + 14:07 死亡的时间线吻合）。
- dim784 从未启动（顺序执行 128 → 256 → 784，wrapper 在 dim256 阶段一并死亡）。

### 排除的原因

| 假设 | 证据 | 结论 |
|---|---|---|
| 机器重启 / 断电 | `journalctl --list-boots`：该 boot 从 07-15 19:07 持续到 07-22 21:00 | 排除 |
| 内存 OOM | 内核日志 07-16 全天无 oom-killer / Out of memory 记录 | 排除 |
| GPU/驱动故障 | 内核日志无 NVRM / Xid 错误 | 排除 |
| 训练代码异常 | Python 异常退出会在退出时刷出 traceback 到日志；两份日志完全为空 | 排除 |

### 判定原因

**运行 runner 的终端 / SSH 会话断开，SIGHUP 杀死了整个进程组**（wrapper、runner、两个训练子进程同时死亡）。证据链：

1. 两张 GPU 上的独立进程与父 runner 在同一时刻（≈14:07:30）消失，只有会话级信号能同时命中三者；
2. 日志为 0 字节：子进程 stdout 重定向到文件后是块缓冲（每个 epoch 的 JSON 行约 1.5 KB，3–6 个 epoch 未到 8 KB 刷新阈值），被信号杀死时缓冲丢失——这是被 SIGKILL/SIGHUP 类信号杀死的典型特征，而 dim128 正常退出时日志完整；
3. `metrics.csv` / `checkpoint_latest.pt` 按 epoch 落盘所以保留了下来，与"进程被突然杀死"一致。

### 脚本缺陷与修复（`scripts/run_highdim_comparison.py`）

| 缺陷 | 后果 | 修复 |
|---|---|---|
| `subprocess.Popen` 未设 `start_new_session`，子进程与 runner 同属终端会话 | 终端断开 → SIGHUP 一锅端 | 子进程用 `start_new_session=True` 放入独立会话；runner 捕获 SIGHUP 后把 stdout/stderr 重定向到 `logs/runner.log` 继续运行 |
| 子进程日志块缓冲 | 被杀时日志内容全部丢失，无法排障 | 子进程注入 `PYTHONUNBUFFERED=1`，逐行落盘 |
| `except Exception` 捕不到 `KeyboardInterrupt`/信号退出 | `runner_status.json` 永远停留在 `running` | SIGTERM 转为 `SystemExit`，`except BaseException` 统一收尾，状态写为 `interrupted` |
| 任务失败终止其余任务时不更新其状态 | 被终止任务状态仍是 `running` | 清理路径统一：终止的任务写 `terminated` 并 `wait()` 回收 |

修复已通过验证：`--dry-run` 全矩阵命令生成正确；信号功能测试确认 SIGHUP 后 runner 与子进程存活且输出转入 `runner.log`，SIGTERM 后子进程被回收、状态文件正确写为 `interrupted`。
